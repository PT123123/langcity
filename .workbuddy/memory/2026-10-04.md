## GDScript 踩坑
`for sx in [-1.0, 1.0]:` 里的 `sx` 推断为 Variant，直接参与算术（`0.3 - i*0.3` 再乘 sx）
会报 `Cannot infer the type of "spread" variable`。要么写 `for sx: float in [...]`，
要么给结果变量显式标注 `var spread: float = ...`。项目里其他文件大量用无标注的
`for sx in [...]` 但只做乘法不做混合运算，所以不报错——**加新算术时要留意**。

## 同日追加：猫的视觉重做（用户反馈"太他妈丑了"）

第一版是拼装玩具，四个硬伤被指出来：
1. **头和身体是两个不相连的球**（浮空零件感）
2. **腿是垂直方盒**（桌面腿感）
3. **背上 4 个黄绿色方块像贴纸**（用 BoxMesh 直接摆在体表）
4. **纯色塑料感**，没有材质层次

### 关键认知：造型原则 > 细节数量
重做的核心原则定成「**任何角度都要有连续的剪影，不能出现浮空零件**」。
按这个原则改完，一口气过了：

| 手段 | 作用 |
|---|---|
| 所有肢体 `BoxMesh` → `CapsuleMesh` | 立刻消除方盒感，有连续曲面 |
| 加**颈胶囊**斜向连接头与肩 | 消除"两个球浮在一起" |
| 虎斑从「方块贴片」→ `TorusMesh` **环绕**躯干 | 贴合体表，不会翘起来像书包 |
| 躯干拆成**两段变径胶囊 + 腰部收窄** | 猫不是等径香肠，要有胸-腰-臀起伏 |
| `sheen` + `rim` 材质 | **「塑料 vs 毛」的分水岭**。Godot 4.2+ 的 StandardMaterial3D 有 `sheen`（绒毛边缘柔光）和 `rim`（轮廓光），没有 rim 角色在亮场景里就是一团糊 |

### 尺寸最终值
`SHOULDER 0.225` / `BODY_Y 0.255` / `BODY_R 0.068` / `BODY_LEN 0.30` / `HEAD_Y 0.385` / `HEAD_R 0.076`
（比第一版整体放大了一圈，腿拉长到 0.095+0.09 才不像桌腿）

### 踩坑
- **`sheen_enabled` / `rim_enabled` 不能假设一定存在**。虽然文档说 4.2+ 有，
  但代码里要用 `"sheen_enabled" in m` 判断后再赋值，否则版本一变就编译失败。
- **贴体装饰件（虎斑环、脊线）会穿出体外**。环的半径必须跟着腰身轮廓走
  （`major = BODY_R * (0.99 - absf(t-0.5)*0.28)`），脊线要从「贯穿全身的长条」
  改成**两段短脊线**。第一版一根长脊线从背穿到腹，转个角度就变成凸刺。
- **调试特写的属性名别猜**：`player.cam.h` 不存在（Camera3D 没这个属性），
  要改弹簧臂长度得用 `player._arm.spring_length`。
- **截图角度选择有坑**：`demo_cat_face` 我设了 yaw=0 结果是怼后脑勺，
  要看脸得设 `yaw = PI` 让相机绕到正面。

### 迭代节奏（截图自检循环）
每改一版跑 `demo_cat_side`（侧面，最能暴露剪影问题）+ `demo_cat_walk`（侧面行走，看步态）。
共迭代 4 版：v1 拼装玩具 → v2 胶囊化+上环+连颈 → v3 细化虎斑/腿/围脖 → v4 加 sheen+rim。

# 同日第三轮：环境贴图（用户反馈"环境也丑，你搞多点贴图啊"）

## 病根不是"贴图少"，是三个用错

项目本来就从 Poly Haven 下过 9 套贴图并接好了 `mat_photo()`，但视觉上等于没用。根因：

### 1. `uv1_scale` 语义误解 → 所有贴图被拉到巨型
`uv1_world_triplanar = true` 时 `uv1_scale` 是**每米重复次数**，不是 UV 倍数。
原来路面传 `0.33` = 一张 1k 贴图铺满 **3 米**，沥青骨料被撑成巨型裂纹。
墙面粉 0.4~0.55 = 铺 2~2.5 米，瓷砖缝全糊掉。
→ 路面要 `1.5`（格子 0.6m，接近真实人行道砖），墙面要 `0.3~0.34`（贴图要密）。

### 2. `albedo_color` 当 tint 用 → 把贴图压死
`tint` 是直接乘 albedo 的。压到 0.44 时，mean=125 的贴图变成 55 = 黑泥。
→ tint 保持在 0.6~0.95，**调亮调暗靠换贴图不靠压 tint**。

### 3. `detail_mask = roughness 图` → 地面出现一摊摊水渍
这是最隐蔽的一个：roughness 的明暗区被当遮罩，在地面上表现成油污水洼。
量化验证 `road_col.jpg` 的大块暗斑是 **0/256 网格**（贴图本身很干净），
证明水渍 100% 来自 mask。→ **不要给 detail_mask 赋 roughness 图**。

## 方法论：选贴图靠量化，不靠肉眼

肉眼在 1k 缩略图上判断不出"放大后会不会显出大特征"。写脚本算三个指标：

| 指标 | 算法 | 含义 |
|---|---|---|
| **色度** | `max(RGB) - min(RGB)` 均值 | 越小越中性。>15 就有色偏 |
| **灰度方差 var** | 缩到 128px 后算方差 | 越小越均匀，放大不显大特征 |
| **大块暗斑** | 16×16 网格均值 < 0.72×总均值的格子数 | 0 = 干净 |

实测结论（`assets/tex/`）：
- `road`(aerial_asphalt_01) **色度 5.9** var=58 暗斑 0/256 → 马路就该用这张，最中性
- `pavement`(concrete_pavement_02) 色度 23.4 var=41 → 均匀但暖米色，铺装偏粉像泳池砖
- `pavers` 色度 20.2 var=123 → 花纹太明显
- `road_alt`(worn_asphalt) 色度 23.2 → 有水渍
- `tilewall` **var=1** → 几乎是纯色深灰（mean 55.8），贴了等于没贴，全部换成 plaster 系
- `plaster` var=10 mean=164.8 → 干净亮，墙面用它

**踩坑**：中途因为"road 有大裂缝"就换掉了它，换成偏色的 pavement —— 是误判。
裂缝靠 `scale` 提到 1.5 就能压掉，不该因此牺牲色度。**先量化再决定，不要凭第一眼印象换图**。

## 环境光照重调（"惨白"的另一半原因）

原来：ambient 0.5 + 冷蓝雾 + 冷色天空环境光 = 整张图发白没颜色。
- ambient_light_energy 0.5 → **0.34**（环境光只补暗部，造型靠太阳）
- 加 `ambient_light_sky_contribution = 0.7` 减天空的冷色贡献
- fog_light_color 冷蓝 `dfe8ec` → **暖米 `e8dfd0`**（远处才有空气感）
- saturation 1.08 → **1.18**，contrast 1.04 → **1.12**（贴图的颜色层次才出得来）
- 太阳角度 -46° → **-38°**（影子更长更可信），energy 1.15 → 1.35
- **加一盏反向补光**（冷色 0.72/0.82/1.0，energy 0.22，不投影）模拟天空 bounced light，
  否则暗部死黑

## Godot 4 API 坑（本轮踩的）

- **detail 相关枚举搬到 `StandardMaterial3D` 了，不在 `BaseMaterial3D`**：
  写 `BaseMaterial3D.DETAIL_BLEND_MIX` / `DETAIL_UV_1` 会报
  `Cannot find member`。正确写法 `StandardMaterial3D.BLEND_MODE_MIX` / `DETAIL_UV_1`。
  文档网页（docs.godotengine.org）写的还是 BaseMaterial3D，**不可信**。
  用 `ClassDB.class_get_integer_constant_list("StandardMaterial3D")` 反射验证才靠谱。
- **`box(size, pos, color, ry, rx, rz, material)`** —— material 是**第 7 个参数**。
  新写 `box(size, pos, someMaterial)` 会报
  `argument 3 should be "Color" but is "StandardMaterial3D"`，要传 `Color.WHITE` 占位。
- **GDScript 的 Color 分量会被钳到 1.0**，写 `Color(0.78, 1.05, 0.7)` 里的 1.05
  等于 1.0，没有意义。想更亮只能靠 `detail_amount` 或换贴图。
- **`Gradient.offsets` 和 `colors` 必须同时设置且等长**，
  否则 `CPUParticles3D.color_ramp` 行为异常。`offsets` 是 PackedFloat32Array。

## 最重要发现：规格里的后处理 API 在 Godot 4.4 上不存在

这是本轮最大的坑，规格文档是按更早/更晚版本写的，多处 API 与 4.4 实测不符：

| 规格写法 | Godot 4.4 实测 | 采用方案 |
|---|---|---|
| `env.vignette_*` | **不存在** | 自建 `assets/shaders/grade.gdshader`（全屏 CanvasLayer） |
| `env.chromatic_*` | 不存在 | 同 shader 内实现 |
| `env.auto_exposure_*` | 不存在 | 手动插值 `tonemap_exposure` |
| `env.adjustment_exposure` | 不存在 | `tonemap_exposure - 1.0` |
| `tonemap_exposure_white` | 实际是 `tonemap_white` | 改名 |
| `SHADOW_PARALLEL_1_SPLIT` | **不存在**（只有 2/4 级联） | 低端用 2 级联 + 缩短 shadow_max_distance |
| `OS.get_video_adapter_memory()` | **不存在** | `get_static_memory_peak_usage()` + GPU 名 SoC 判断 |
| `BaseMaterial3D.DETAIL_BLEND_MIX` | 枚举搬到 `StandardMaterial3D` | `StandardMaterial3D.BLEND_MODE_MIX` / `DETAIL_UV_1` |

**方法论：官方文档网页（docs.godotengine.org）不可信** —— 它仍写 BaseMaterial3D。
必须用反射验证：
```gdscript
ClassDB.class_get_integer_constant_list("StandardMaterial3D")   # 枚举
Environment.new().get_property_list()                            # 属性
ClassDB.class_get_method_list("OS", true)                        # 静态方法
```
写个 `/tmp/probe.gd` 用 `--headless --script` 跑，几秒就能查准。

## shader 全屏调色层的两个坑

1. **canvas_item 的 `TEXTURE` 是 ColorRect 自己的空白纹理** —— 直接采样会把全屏刷白。
   必须显式声明 `uniform sampler2D screen_tex : hint_screen_texture`。
2. 输出 `COLOR = vec4(col, 1.0)` 会覆盖 alpha；用 `COLOR = vec4(col, COLOR.a)`。

## 夜景/黄昏的曝光配比（靠踩坑得出）

**夜景不能用「低能量 + 负曝光」**。第一版给了 `sun_energy 0.14` + `exposure_bias -0.45`，
结果整个画面糊成黑块。正确做法：
- 月光弱但**有方向**（energy 0.45，不是 0.14）
- ambient 提上来（0.5）保证轮廓可读
- 靠人工点光 + 自发光做明暗层次
- `exposure_bias` 甚至可以是**正的**（+0.15）

黄昏同理：`-0.25` 太压，改 `0.0`。

## 材质工厂的核心不是加细节，是拉档

20 个材质语义工厂，**关键是 roughness / metallic 拉开档**：
塑料 0.35 / 金属 0.42+metallic **0.85** / 混凝土 0.88 / 玻璃 0.06 / 和纸 0.95 / 沥青 0.95。
**metallic 低于 0.3 看起来还是塑料** —— 这是最关键的一条。

**材质微差技巧**（`_mat_j` / `_jitter_color`）：按世界坐标哈希生成缓存 key，
让每块砖/每扇窗/每棵树冠拿到独立材质实例，明度抖动 ±5.5% + 轻微色相偏移。
消除「同一个紫出现 200 次」的塑料感 —— 规格说的「顶点色微差」，用材质实例实现更简单。

**Bloom 铁律**：`emission_energy_multiplier` 必须 **> 1** 才会被 Bloom 捕获。
低于 1 就是块白板。信号灯 3.0 / 路灯 3.2 / 贩卖机灯箱 2.6 / 霓虹 4.0。

# 同日第五轮：跳跃 + 缩小猫（用户反馈"只能走不能跳，猫太大"）

## 诊断：两个问题其实是同一个

用户说「Stray 能跳到桌子上，这只猫只能走；而且猫太大」。
查下来发现根因是**尺度体系完全不匹配**：

| 项 | 改前 | 问题 |
|---|---|---|
| 猫碰撞体 | 0.44m 高 | 肩高 0.28m，比真实猫（0.23m）大 22% |
| 垃圾桶 | 0.85m（实心到顶） | 猫撞墙，跳不上 |
| 邮筒 | 1.0m（实心到顶） | 同上 |
| 长椅 | 0.85m（实心到顶） | 同上 |
| 碰撞体结构 | **全部从地面到顶的整块实心盒** | 猫只能绕过去，没有任何落脚点 |

**关键发现**：之前所有 META 里的 `solid` 都是"从地面一路到顶"的实心长方体。
所以哪怕加跳跃，猫也跳不上任何东西 —— 因为没有平台可站。
这是比"缺跳跃"更根本的问题。

## 跳跃高度是解析量，先算再调

`h = v²/(2g)`，g=19 时：

| v | 跳高 | 倍体高 |
|---|---|---|
| 4.35（初版） | 0.50m | 1.4 |
| **5.0（采用）** | **0.66m** | **1.8** |
| 5.4 | 0.77m | 2.1 |
| 5.8 | 0.89m | 2.5 |

选 v=5.0 → 跳高 0.66m = 1.8 倍体高（真实猫 1.5~2 倍）。
**第一版 v=4.35 只能跳 0.5m，而场景里最矮的"能跳的"物件也有 0.85m —— 一个都跳不上。**
这是纯数字推演发现的，不测不知道。

## 最终尺度表（8 类可跳，全在 0.66m 以下）

| 物件 | 台面高 | 台面层厚度 |
|---|---|---|
| 井盖 pipe | 0.38m | 0.10 |
| 箱子 crate | 0.40m | 0.10 |
| 长椅 bench | 0.42m | 0.12 |
| 自行车 bicycle | 0.50m | 0.10 |
| 垃圾桶 trash | 0.52m | 0.12 |
| 邮筒 mailbox | 0.55m | 0.12 |
| 矮墙 lowwall | 0.55m | 0.14 |
| 花坛 planter | 0.50m | 0.14 |

猫：`CAT_HEIGHT 0.36` / `CAT_RADIUS 0.15` / 视觉缩放 0.82

## META 新增 `stand` 参数 = 台面层厚度

这是核心机制。`stand > 0` 时碰撞体**只在物件顶部生成该厚度的薄层，脚下是通的**：

```gdscript
if top_only:
    sbox.size = Vector3(sv.x, stand_h, sv.z)
    ss.position = Vector3(0, sv.y - stand_h * 0.5, 0)   # 顶面对齐原 solid 顶部
else:
    sbox2.size = sv          # 实心，从地面到顶
```

意义：
- 猫可以从**侧面**走到物件旁边、跳上去
- 台面是薄层，视觉上物件底部镂空，不违和
- 落台判定靠薄层的上表面

## 跳跃手感三件套（缺一个就"跳不动"）

```gdscript
const JUMP_VELOCITY := 5.0
const JUMP_CUT := 0.45      # 可变跳跃高度：上升途中松手减速
const COYOTE := 0.12        # 离开边缘后仍可跳
const JUMP_BUFFER := 0.14  # 落地前提前按跳也生效
const AIR_CONTROL := 0.55   # 空中操控力
const STEP_HEIGHT := 0.3    # 自动上台阶（路缘石直接走上去）
```

- **coyote time**：走出边缘的瞬间还能跳，否则玩家会觉得"边缘判定太严"
- **jump buffer**：落地前 0.14s 内按跳，落地立刻生效。手游必需
- **可变跳跃高度**：轻点小跳、重按大跳。`if velocity.y > 0 and not jump_held: velocity.y -= GRAVITY*JUMP_CUT*delta*8`
- **屏幕按钮必须用 `button_down`/`button_up` 而不是 `pressed`**：`pressed` 只在抬起时触发，
  做可变跳跃高度会完全失灵

## 落地 squash & stretch

if on_floor and not _was_floor:

# 同日第六轮：材质重做（用户反馈"环境太丑，材质什么的做好看"）

## 诊断：三个病因叠加，量化后一目了然

截图看到「墙、窗、招牌全是同一个紫灰色，贴图完全没显出来」。逐个量化后：

### 病因 1：`albedo_color` 是**乘**贴图，不是调色叠加

```gdscript
# 之前的写法（错）：
m.albedo_color = tint          # tint=(0.93,0.9,0.86) → 贴图被压到 93% 并染米色
```
`albedo_color` 直接乘 `albedo_texture`，任何明显偏离 1.0 的 tint 都会
**把贴图的明暗层次（灰缝、污渍、颗粒）全部压平** → 墙面变成纯色块。

修法：加 `_soft_tint()`，把 tint 归一化到接近白色。
```gdscript
static func _soft_tint(tint: Color, strength: float) -> Color:
    var lum := (tint.r + tint.g + tint.b) / 3.0
    # 映射到 [0.82, 1.0] —— 「几乎不压暗」区间
    var norm := inverse_lerp(0.55, 1.0, clampf(lum, 0.0, 1.0))
    var target := lerpf(0.82, 1.0, norm)
    # 色相偏移只保留一点点
    var keep := clampf(strength, 0.0, 1.0)
    var ratio := 1.0 / maxf(lum, 0.001)
    return Color(target * lerpf(1.0, clampf(tint.r * ratio, 0.85, 1.12), keep), ...)
```
并把所有调用点的 `tint_amt` 从 `0.0` 改成 **0.85~0.92**。
**原则：tint 尽量接近白色，"上色"这件事交给不同贴图本身去完成，
不要用同一张贴图 × 不同 tint 去硬染**（那正是"全糊成一片紫灰"的原因）。

### 病因 2：好几张贴图本身就「太平」

量化所有贴图（缩到 96px 算灰度方差）：

```
★太平（var<30，不能单独用）
  plaster          var=10    ← 之前所有墙都用它，等于没贴图
  concrete         var=17
  concrete_wall_001 var=10
  block            var=23
  bark_cedar       var=20    ← 树干
  dirt             var=15
  dirt_path        var=34
有细节（var 60~250，适合大面积）
  grass 61 / grey_plaster 89 / pavers 104 / rustic_stone_wall 121
  roof 178 / plaster_alt 237 / brown_planks_08 211
高对比（var>300，适合点缀/小面）
  red_brick 323 / brick 360 / worn_brick 392 / plaster_brick_01 320
  yellow_brick 519 / dark_planks 609
```

**var < 30 的贴图放大后就是纯色块**，比没有贴图更糟（因为它吃掉了 detail 层）。
从缓存搬入 13 套墙/砖/木贴图，替换掉所有太平的。

### 病因 3：所有建筑用同一张贴图

改成**不同建筑用不同贴图**（靠贴图本身做区分）：
- 商店门脸 → `plaster_brick_01`（320，抹灰+砖混搭，日式町屋常见）
- 民居墙 → `grey_plaster`（89）
- 公寓墙 → `plaster_alt`（237，抹灰有斑驳）
- 咖啡馆下层 → `brown_planks_08`（211）
- 咖啡馆上层/拉面店 → `plaster_brick_01` / `dark_planks`（609，深色木配居酒屋）
- 邮局 → `yellow_brick`（519，黄砖墙很配邮局）
- 车站 → `grey_plaster`（干净浅色）
- 民居围墙 → `rustic_stone_wall`（121）
- 树干 → `bark`（363）

## 关键修复：环境光源 COLOR → SKY

```gdscript
# 之前（错）：
env.ambient_light_source = Environment.AMBIENT_SOURCE_COLOR
# 之后：
env.ambient_light_source = Environment.AMBIENT_SOURCE_SKY
env.ambient_light_sky_contribution = 0.5
```

**COLOR = 只取一个纯色当环境光** → 天空的橙紫渐变完全不参与照明 →
阴面死黑、所有材质受光一致 → 画面平、像贴纸。
**SKY = 用天空贴图算环境光（bounced light）** → 阴面被天空冷/暖色自然补亮，
这是黄昏/夜景能有层次的**物理基础**。改完之后路面骨料纹理才显现出来。

0.5 是平衡点：纯 SKY(1.0) 太蓝，纯 COLOR(0) 太平。

## 玻璃之前是不透明的

## 踩坑：`_base_m`（世界底层）用高对比贴图会整片透出来
